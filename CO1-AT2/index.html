1. HTTP Response Analysis

Given response: HTTP/1.1 200 OK, Date: Mon, 01 Apr 2026 10:00:00 GMT, Content-Type: text/html, Content-Length: -150, Connection: keep-alive

Incorrect or invalid fields

The displayed fields have been run together; actual HTTP headers must be separated by CRLF line breaks. The invalid field is Content-Length: -150.

Content-Length issue and impact

Content-Length must be a non-negative decimal number giving the exact number of bytes in the message body. A negative value is invalid. The browser cannot reliably identify the end of the body, so it may reject the response or be unable to reuse the keep-alive connection safely.

Status-code correctness

200 OK is the correct status for a successfully processed request that returns an HTML representation. However, the malformed header makes the response itself invalid.

Corrected response

HTTP/1.1 200 OK
Date: Wed, 01 Apr 2026 10:00:00 GMT
Content-Type: text/html; charset=UTF-8
Content-Length: 150
Connection: keep-alive

The date has also been corrected: 1 April 2026 is a Wednesday. The length must equal the real response-body size; otherwise use a valid transfer-framing method such as chunked encoding.

Missing or improperly closed element

The opening <p> tag has no closing </p> tag.

Browser interpretation and rendering impact

HTML parsers recover from this error by implicitly closing the paragraph before the closing </div>. It will normally render as a paragraph inside the div. In larger documents, implicit closing can create unexpected DOM structures and affect CSS, JavaScript, spacing, and accessibility.

3. GET vs POST in a Login System

AspectGETPOST
TransmissionAppends parameters to the URL query string.Places form data in the HTTP request body.
VisibilityCan appear in history, logs, bookmarks, referrer headers, and shared links.Not displayed in the URL, but still needs HTTPS for protection in transit.
Login suitabilityNot suitable.Appropriate for submitting credentials.

Analysis

POST is more suitable because it does not expose credentials in the URL and login establishes authentication state. “In the request body” is not the same as encrypted; HTTPS is mandatory.

Security risks of GET

A password in the query string can be retained by browser history, server and proxy logs, analytics tools, bookmarks, screenshots, and Referer headers. This can expose credentials to unauthorized people or systems.

Secure login practices

  • Use POST over HTTPS; never send credentials in a URL.
  • Hash passwords with Argon2id or bcrypt and a unique salt; never store plain-text passwords.
  • Use Secure, HttpOnly, SameSite cookies and regenerate the session ID after login.
  • Validate input server-side, rate-limit failed attempts, use generic error messages, and never log passwords.

5. Browser–Server Communication Flow

StepInterpretation
1. URL enteredThe browser parses the scheme, hostname, path, and query, then checks applicable caches and security policies.
2. DNS lookupDNS translates a domain name into an IP address. A cached answer can avoid a network lookup.
3. HTTP requestThe browser establishes a connection—typically TCP plus TLS for HTTPS—and sends a request such as GET.
4. Server processingThe server authorizes the request, runs application logic, possibly accesses a database, and prepares the response.
5. Response returnedThe server sends a status line, headers, and usually an HTML body.
6. Browser rendersThe browser builds the DOM, loads assets, applies CSS, lays out, and paints the page.

Possible delays

Delays can occur during DNS resolution, connection and TLS setup, redirects, server queues, database/API calls, response transfer, and downloading or rendering CSS, JavaScript, fonts, images, and third-party resources.

Role of DNS

DNS is the naming layer that converts a human-readable host name into the network address needed to reach the server. If DNS is slow or unavailable, the website cannot normally be reached.

Performance optimizations

Use reliable DNS and caching, HTTPS with HTTP/2 or HTTP/3, keep-alive connections, a CDN, compression (Brotli/Gzip), cache-control headers, optimized and lazy-loaded images, fewer redirects, deferred non-critical scripts, and efficient server/database operations.
